The Map
That Forgets

A custom hash map in Go that tracks a billion series and forgets each one after 20 idle minutes

Oleg Zaytsev Grafana Labs · Mimir github.com/colega
[0:00] Hi. I'm Oleg, I work on Grafana Mimir. This talk is about one data structure: a hash map that we built for one very specific job. It holds a lot of series hashes, and it forgets them. Most of the talk is about the forgetting part, because that turned out to be the hard part. The background is the map: orange slots get written, the yellow sweep is the cleanup, red flashes are slots being forgotten.
The problem

Series limits, before Kafka

[0:40] Mimir is a horizontally scalable Prometheus backend. The new ingest architecture puts Kafka between the distributors and the ingesters. (step) Problem: every tenant has a max series limit. With Kafka in the middle, we only find out that a series is over the limit after we wrote it to Kafka. We paid for it, block-builders have to enforce the limit again on their own, and the client never gets the error. (step) So we built the usage-tracker. The distributor sends the series hashes, the usage-tracker answers with the rejected ones, and the client gets a 429. Before Kafka.
The job

The whole service is one map


// conceptually
var series map[uint64]time.Time

func track(hash uint64, now time.Time) (rejected bool) {
	if _, ok := series[hash]; !ok && len(series) >= limit {
		return true
	}
	series[hash] = now
	return false
}

// every minute
for h, t := range series {
	if now.Sub(t) > 20*time.Minute {
		delete(series, h)
	}
}
  • Keys are series hashes: already random uint64
  • Value is "last seen", minute precision is enough
  • Every push request updates thousands of keys
  • Every minute, forget what was idle for 20 minutes
  • Hash collisions? We accept them. It is a protection, not billing.
[1:40] If you squint, the service is this map. A key is the hash of the series labels. The value is when we saw it last. Track checks the limit and updates. Once a minute we delete what was idle for 20 minutes. The rest of the service is replication through Kafka, snapshots, partitions, rings. Today I only talk about this map.

01

One byte of time

Why store 8 bytes of timestamp if you only care about the last hour?

[3:30] First design decision: the value.
clock.Minutes

A 2-hour clock face


// Minutes passed since the last 2-hour boundary.
// Only makes sense within the last hour.
type Minutes uint8

func ToMinutes(t time.Time) Minutes {
	return Minutes(t.Sub(t.Truncate(2 * time.Hour)).Minutes())
}
13:35 is 95: one byte, and 7 bits are enough
Valid window: the last 60 minutes
Watermark = now - 20 min. Older series expire
14:10 is 10. And 10 is after 115.
[3:45] We don't need nanoseconds, cleanup runs once a minute. We don't need years either: the idle timeout is at most one hour. So the value is the number of minutes since the last even hour. 13:35 is 95. That is one byte. (step) Only the last hour is valid. (step) The watermark is now minus 20 minutes. Everything at or behind it expires. (step) Cleanup removes them. (step) The catch: it is a clock. At 14:10 the value is 10, and 10 must compare as newer than 115. So GreaterThan is not a plain comparison. Remember that, it comes back as a branch-prediction problem.
The first trick

Zero must mean empty


// xorData is what we store in data.
// By storing xor-ed values, our empty data
// represents an empty dataset.
type xorData uint8

func xor(v clock.Minutes) xorData { return xorData(^v) }

const (
	empty     = 0b0000_0000
	spillmark = 0b0000_0001 // later!
)
Minute 0 is a valid value. If we store it as-is, we can't tell it from "no value here".
Store ^minutes: minute 0 becomes 0xff, and 0x00 is free to mean empty.
make([]data, n) is already an empty map. No fill loop, the kernel gives zeroed pages for free.
Cost: 0xff and 0xfe can't be stored. Fine, we only need 0..119.
[5:00] Small trick, but everything later depends on it. We invert the minutes before we store them. So zero bytes mean empty slot, and one means a spillmark, which you'll meet later. Other Swiss tables use a non-zero byte for empty, and they have to fill the control bytes on every allocation. We don't: make() is the empty map.
02

A Swiss table, but ours

Based on dolthub/swiss, then mostly rewritten for one job

[5:45] Now the container.
Layout

Groups of 8 slots, three arrays

index 1 byte per slot: 7 bits of the hash + 2. Find candidates without touching keys.
data 1 byte per slot: the xor-ed minutes.
keys 8 bytes per slot: the full hash, only read to confirm a match.
80 bytes per group, 64 are keys. Load target is 50%, so 20 bytes per series.
[6:00] Like a Swiss table: slots in groups of 8. For each group we have an index word, a data word and the keys. (step) index is one byte per slot, a prefix of the hash. Plus 2, so 0 and 1 stay reserved. (step) data is one byte per slot. (step) keys are 8 bytes per slot. Look at the proportions: the keys are huge. One group of keys is exactly one cache line. (step) So four fifths of the memory is keys. Cleanup only needs data. That shapes everything later: avoid touching keys.
SWAR: SIMD within a register

8 slots, one uint64, no loop

Looking for prefix 0x47
Broadcast it to all 8 bytes
XOR: matching bytes become 00
Find zero bytes: slots 1 and 3. Now compare 2 keys, not 8.

func (m *index) match(p prefix) bitset { return findZeroBytes(castUint64(m) ^ (loBits * uint64(p))) }
func findZeroBytes(x uint64) bitset    { return bitset(((x - loBits) &^ x) & hiBits) }   // loBits = 0x0101..01, hiBits = 0x8080..80
[7:15] The classic Swiss table trick, without SIMD instructions. Read the 8 index bytes as one uint64. Multiply the prefix by 0x0101..01 to put it in every byte. XOR: matching bytes become zero. Then the old bit hack from Stanford's bithacks page finds the zero bytes in one subtract and two ANDs. The result has the high bit of every matching byte set, and TrailingZeros gives us the slot. It can report a false positive, that's fine: we compare the full key anyway. Keep this idea in mind. We use it again for the cleanup, on data, with arithmetic.
December 2024 · hackathon

The first version: key and value in one uint64

The key is already a hash: no hashing in the map.
Top 7 bits go to the index.
128 shards: the low 7 bits are the shard, the same in every key of the map. Useless!
Put the value there. One uint64 per series, and Cleanup reads one array.

const valueBits = 7 // Shards = 1 << valueBits = 128

m.data[i][s] = masked | uint64(value&valueMask^valueMask) // key AND value
[8:30] This started in a hackathon in December 2024, on a branch. Keys are already hashes, so we don't hash again. (step) Top bits go to the index. (step) Then I noticed: with 128 shards, a shard holds the keys with the same value modulo 128. So all keys in one map have the same low 7 bits. 7 bits that carry no information. (step) And our value is 7 bits! So the value went into the key. One uint64 per series. I was very proud of this one.

July 2025 · productionizing

Reality: 128 shards per tenant is too many

Most tenants are small. 128 maps each is a lot of fixed cost.
The shard count becomes configurable. The low bits of a key are not a fixed free field anymore.
So keys get their own array. "This is up to 14% slower than fixed shards." Accepted.

Put is not where you win. Forgetting is.

[10:30] When we productionized it in summer 2025, 128 shards per tenant was too much fixed overhead for small tenants. We went to 16, and made the shard count a parameter of the map. Once the count is not a fixed 128, the low 7 bits are not free anymore, so the keys got their own array. I measured it, it was up to 14% slower, and we accepted that. How does it compare to a plain Go map today? Go maps are Swiss tables since 1.24, so Put is the same: it's one cache miss either way. Memory is a bit better. But cleanup is 11 times faster, because we only scan the data bytes. That's where the rest of this talk goes. It went to main in August 2025, PR 12358, 19 thousand lines.
03

Forgetting is hard

Open addressing doesn't like deletes

[11:45] So, deletes.
Linear probing

Why you can't just clear a slot


// The rule that makes a lookup stop:
// "this group has a free slot, so insert would have used it"
if m.index[i].matchEmpty() != 0 { break } // not found
[12:00] Open addressing with linear probing. X belongs in group 0, but group 0 was full when X arrived, so it went into group 1. (step) A lookup for X walks: group 0, no X, no empty slot, so X might be further. Group 1: found. (step) Now cleanup removes C. If we just clear the slot... (step) ...the next lookup for X stops at group 0, because there's an empty slot. X is gone. Worse, X is still there, so the next put counts it as a new series, against the limit. (step) The textbook fix is a tombstone: deleted, but keep walking.
Three generations of delete

Before cleanup

written by cleanup not touched tombstone spillmark 

// v1: a removal writes all three arrays
m.index[i][j] = tombstone
m.keys[i][j] = 0
m.data[i][j] = 0
m.dead++
    

// v2 lookup: stop probing if the last slot is empty (not busy and not a spillmark)
if m.index[i][last] == empty {
	break
}
[13:30] Here is one group, with all three arrays. Everything but A expires. (step) Version 1 is the textbook: tombstone in the index, zero the key, zero the data. 21 writes, and the keys line is dirty now, which is the 64-byte line. The tombstone slot can't be reused until the next rehash, and when half of the map is dead we rehash the whole shard, under the lock. (step) In April I noticed that groups are half full on average, so usually there is a free slot. If the group has a free slot, nobody was pushed past it. Then we can move the last element into the hole and no tombstone is needed. Much fewer rehashes. But we still write keys. (step) Then the real insight: a lookup doesn't need to know which slot was deleted. It only needs one bit per group: was this group ever full? A group is full exactly when its last slot is taken. So we put a mark only in slot 7. The spillmark. Probing continues while the last slot is not empty. Keys are never written by cleanup: stale keys are unreachable because the index byte gates the key comparison. Two words written, six slots free, and even the spillmark slot is reusable by insert.
Spillmark quirks

Things the tests found

The infinite lookup

Only a rehash sets a last slot back to empty. If every group's last slot is taken, a lookup for a missing key walks forever.


if i == ps {
	// We're back where we started: every group has its
	// last slot taken, so |key| is not in the map.
	break
}

The rehash loop

Too many spilled groups → re-pack at the same size. But a fresh re-pack can fill half of the groups. So the threshold is half + 1.


func (m *Map) maxSpilledGroups() uint32 {
	return uint32(len(m.index))*maxAvgGroupLoad/groupSize + 1
}

Rolled out side by side: v1 and v2 behind -usage-tracker.tenantshard-impl-version. Three weeks later: -974 lines, v1 gone.

[15:30] Two quirks. First: a lookup walks until it finds a group whose last slot is empty. Only a rehash makes a last slot empty again. So if all groups have their last slot taken, looking for a missing key never ends. The counter should prevent that state, and it did once it counted right, but a loop shouldn't depend on a counter maintained somewhere else to terminate. So: if we're back at the start, stop. Second: when too many groups spilled, we re-pack at the same size. A fresh re-pack can leave half of the groups full, so the threshold has to be half plus one, or every re-pack triggers the next one. And you don't swap the storage engine of a running fleet and hope. v1 and v2 lived side by side behind a flag, we switched cells one by one, and three weeks later v1 was deleted.
04

Cleanup at 64 slots per branch

The scan holds the shard lock. Every request of that tenant waits for it.

[16:30] Deletes are cheap now. But the scan still visits every slot, every minute, under the lock.
Branch prediction

The 2-hour boundary is a coin flip

before

func (m Minutes) GreaterThan(other Minutes) bool {
	if m > other {
		return m-other < 60
	}
	return int(m+(2*60))-int(other) < 60
}

func (m Minutes) GreaterOrEqualThan(other Minutes) bool {
	return m == other || m.GreaterThan(other)
}
after (#16778)

func (m Minutes) aheadOf(other Minutes) int64 {
	d := int64(m) - int64(other)
	// d>>63 is -1 if d is negative, 0 otherwise:
	// this adds 120 only when d is negative.
	return d + (d>>63)&120
}

func (m Minutes) GreaterOrEqualThan(other Minutes) bool {
	return uint64(m.aheadOf(other)) < 60
}
Series live on both sides of 0: some at 115, some at 5.
So m > other is random per series, and the CPU mispredicts.

Cleanup of 1M series, M3 Pro

[16:45] Remember the clock face. Comparing on a clock needs a branch: is m bigger than other? Near the 2-hour boundary, half of the series are at 115 and half at 5, so that branch is a coin flip, and the CPU mispredicts all the time. (step) Compute the distance with a sign mask instead: shift right by 63 gives all ones if negative, AND with 120 adds 120 only then. One unsigned range check. 21% faster across the boundary, and the same otherwise.
SWAR cleanup · #16825

Compare 8 clocks with one subtraction

Same steps as aheadOf, in every byte at once. Borrows never cross a byte.
One branch per 64 slots. A block with nothing to remove is not written.

for b := 0; b < len(m.data); b += groupsPerBlock {   // "The loop below is intentionally unrolled and doesn't use helper functions,
	x[0] = *groupWord(&d[0]) // ... x[7]           //  as those helpers become too expensive to inline."
	r[0] = expiredSlots(x[0], w) &^ freeSlots(x[0]) // ... r[7]
	if r[0]|r[1]|r[2]|r[3]|r[4]|r[5]|r[6]|r[7] == 0 { continue }
	removed += clearSlots(&idx[0], &d[0], x[0], r[0]) + /* ... */ clearSlots(&idx[7], &d[7], x[7], r[7])
}
[18:00] Now we can do the same thing as the index match, on the data. 8 groups of data are 64 bytes, one cache line. We call it a block. (step) Zoom in on group 0. We put the watermark in every byte and do the aheadOf arithmetic on the whole uint64. The trick: set the high bit of each byte in one operand and clear it in the other, so a subtraction never borrows into the next byte, then fix the high bits with XOR. The result: a high bit in every expired byte. (step) OR the masks of the 8 groups. If it's zero, skip the block, no writes. That is one branch per 64 slots, and in steady state most blocks have nothing to remove. (step) Otherwise write the block: expired slots become empty, a last slot becomes a spillmark.
The scary part

It is just aheadOf(w, v) < 60


func expiredSlots(x, w uint64) uint64 {
	v := ^x // The clock.Minutes of every slot, see xorData.

	// d := watermark - v. Setting the high bit of each byte of w and clearing it in v means that no byte
	// borrows from the next one. The xor then restores the high bits. Note that ^v is x.
	d := ((w | hiBits) - (v &^ hiBits)) ^ ((w ^ x) & hiBits)
	// d < 0, that is watermark < v: the borrow out of the high bit of each byte.
	negative := ((^w & v) | (^(w ^ v) & d)) & hiBits
	// aheadOf := d + (d>>63)&120. 120 fits in the low 7 bits, so adding it to the low 7 bits of each
	// byte never carries into the next byte, and the xor adds the high bits back.
	aheadOf := ((d &^ hiBits) + (negative>>7)*120) ^ (d & hiBits)

	// aheadOf < 60: adding 128-60 to the low 7 bits sets the high bit when they are 60 or more,
	// and a byte that already has its high bit set is 128 or more.
	return ^(((aheadOf &^ hiBits) + loBits*(128-60)) | aheadOf) & hiBits
}

Tested exhaustively: every watermark × every value, against clock.Minutes.GreaterOrEqualThan.

[19:15] This is the whole thing. It looks scary, but it's the three lines of aheadOf, per byte. (step) Subtract without borrows. (step) Find which bytes went negative. (step) Add 120 to those, without carries. (step) Check less than 60, with the same high-bit trick. And because the input space is tiny, 256 times 256, the test checks all of it. Not a property test, the full space.

05

It's the lock, not the map

p99 doesn't care how fast you scan. It cares how long you hold the mutex.

[21:15] Last part. Everything so far made the map faster. But the latency of a request is about how long it waits for the lock.
Snapshots · #16882

The one-character fix


func pooledClone[T any](input []T, pool *sync.Pool) *[]T {
	pooled := pool.Get().(*[]T)
	if cap(*pooled) > len(input) { // was never true
		*pooled = (*pooled)[:len(input)]
	} else {
		*pooled = make([]T, len(input))
	}
	copy(*pooled, input)
	return pooled
}

A slice from make has cap == len. A shard of a stable size never hit the pool. Every snapshot allocated and page-faulted 514 MB under the lock.

(step) One character. 230 milliseconds to 15. (step) And if you try to test it: the race detector makes sync.Pool drop items randomly. I learned that the fun way.
Snapshots · #16892

15 ms is still 15 ms. Take the lock in chunks.

Copy 16K groups under the lock (1 MB of keys), unlock, then scan the copy.
A rehash during iteration? It allocates new arrays and never writes the old ones again. Keep reading them, no lock needed.
[22:30] 15 ms is still a stall for every request of that tenant. So Iterate copies 16 thousand groups at a time under the lock, releases it, and scans the copy. (step) 460 short holds instead of one long one. 24 microseconds on average, 110 at most. The fun part is the rehash. My first version restarted iteration on rehash, with a fallback. Then the simpler idea: a rehash allocates new arrays and never touches the old ones. So once a rehash happens, keep reading the old arrays, without the lock. The closed PR says "superseded by a simpler approach". Then we deployed it, and the p99 spikes were still there. They had moved: loading the other zone's snapshot held the lock for 100 to 200 ms per shard. Same fix: 16K puts per lock hold.

Takeaways

What I'd tell myself in 2024

Know your data. Keys are hashes, values fit in a byte, time is a clock.
Zero means empty. make gives you the empty map for free.
Benchmark the boring paths. Put was fine from day one. Delete, cleanup and snapshots were not.
Random data breaks branches. SWAR is SIMD in plain Go, on every arch.
A lock hold is a latency budget. Chunk it.
Ship side by side. Behind a flag, then delete the old one fast.
[24:00] If you take one thing: know your data. Every trick in this talk came from a property of the data, not from a generic hash map paper. Still open: Cleanup holds the lock for the whole shard. That's next, with the same chunking pattern.
